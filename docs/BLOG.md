# Folio blog

Apply `supabase/migrations/009_blog.sql` in the Supabase SQL editor after migrations 001–008. It creates posts, private revisions, likes, and the `folio-blog` image bucket. The existing Supabase URL, publishable key, service role key, and Google sign-in configuration are sufficient; the editor requires no additional API key.

In Supabase **Authentication → URL Configuration**, allow the application's callback URLs with their `next` query parameter so Google/email sign-in can return to an article or editor. A callback-scoped pattern such as `http://localhost:3000/auth/callback**` covers local development; use your exact HTTPS hostname with `/auth/callback**` for production. Keep the hostname fixed to your own application. The application validates return destinations separately. See [Supabase redirect URL patterns](https://supabase.com/docs/guides/auth/redirect-urls). This is the application return URL; Google's authorized OAuth redirect URI remains the Supabase callback.

Sign in as an assigned super admin and open **Super admin → Blog posts**, or `/admin/blog`. Choose **New post** to start a cloud draft. The editor supports headings, bold, italic, underline, strike, highlights, alignment, lists, quotes, code, links, images, resizable tables, undo/redo, and reader preview. Post settings contain the slug, excerpt, author, category, tags, cover image, featured badge, and SEO fields. Focus mode hides the inspector. `Ctrl/Cmd+S` saves immediately; changes also autosave after two seconds.

**Save draft** keeps changes private. **Publish** makes the current draft public; **Publish changes** explicitly replaces the live version. Choose a future local date/time to schedule publication. Public reads filter by the publication timestamp, so scheduling needs no cron job. The last 30 saved versions can be restored into the draft. Concurrent saves use version checks, and a failed write preserves the editor content. Keep the tab open and retry a failed save; reload after reviewing a conflict from another tab.

The post manager supports title search, status filters, pagination, duplication, Trash, and restoration. Trash immediately removes a post from public access. Restoring returns it to draft status. Trash retains the document, revisions, likes, and images for recovery; it does not permanently purge media. Blog images are public editorial assets, separate from customers' private PDF storage allowances. Uploads accept JPEG, PNG, and WebP up to 5 MB; the server verifies and converts images to WebP, strips metadata, and limits dimensions to 2200 pixels. Only admin routes can upload.

Readers visit `/blog` and `/blog/[slug]`. Articles are server-rendered, searchable by title and category, and include canonical URLs, Open Graph/Twitter metadata, `BlogPosting` and breadcrumb structured data, and sitemap entries. Drafts, scheduled posts before their publication time, and trashed posts are unavailable publicly. Reader pages and the public listing do not expose unpublished revisions. Google sign-in returns a reader to the article; each account can like or unlike a post once. Deleting an account removes its likes and updates the count. Suspended accounts cannot like posts.

For production SEO, set `NEXT_PUBLIC_SITE_URL` to the real HTTPS origin and `NEXT_PUBLIC_INDEXABLE=true`, as described in the existing setup guide.

Verification: `npm test` includes real PostgreSQL policy and server-route tests with isolated Supabase transport. `npm run test:auth` includes the writing workspace and role checks. `npm run test:blog` runs public article, SEO, responsive layout, accessibility, sign-in return, and persistent-like tests against a local Supabase fixture. The two browser suites both use port 3001 and `.next-auth-tests`; run them sequentially. No fixtures contact the real Supabase project or publish example posts there.
